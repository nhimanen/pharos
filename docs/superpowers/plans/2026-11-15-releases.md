# Pharos Releases and Safe Index Upgrades — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship versioned GitHub releases, and make sure an index built by an incompatible pharos version is never searched silently.

**Architecture:**
- An `index-format.json` stamp per project records the index format and the pharos version that built it.
- `IndexFormat` compares the stamp against `IndexVersions.INDEX_FORMAT`. Read paths refuse a mismatched project; cross-project searches skip it with a warning. Full index runs write the stamp, and incremental runs on a mismatched index become full runs.
- Two new commands: `index-status` reports format status and `upgrade-indexes` re-indexes outdated projects.
- `setup.sh` gains a release-download mode, an upgrade-time warning and `--upgrade-indexes`.
- A tag-triggered GitHub Actions workflow builds, tests and publishes the release.

**Tech Stack:** Java 25, Maven (resources filtering, shade), picocli, Javalin, Jackson, JUnit 5 + AssertJ, bash, Python 3 (the `./pharos` CLI), GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-15-releases-design.md`

## Global Constraints

- `IndexVersions.INDEX_FORMAT` is an `int` separate from `CHUNKING_VERSION`. Its starting value is **1**. A missing stamp means format **0**.
- Stamp file: `<project index dir>/index-format.json`, content `{"format": <int>, "pharosVersion": "<x.y.z or dev>", "writtenAt": "<ISO-8601>"}`.
- Only **full** index runs write the stamp. An incremental run on a mismatched format is turned into a full run, printing `index format changed (<old> → <new>): running a full re-index`.
- Mismatch message content (spec): `Project '<p>' was indexed by pharos <v> (index format <n>); this pharos (<v2>) needs index format <m>. Run: pharos index --full <p>   (or upgrade all: ./setup.sh --upgrade-indexes)`. A **newer** stamp gets wording that the index is newer and says to re-index or reinstall the newer version.
- Status values: `ok`, `outdated`, `newer`, `missing`.
- `CHUNKING_VERSION` behaviour is unchanged, and it never triggers the read-time check.
- First release: `v1.4.0`. The `pom.xml` version becomes `1.4.0`.
- Release tags match plain `v[0-9]+.[0-9]+.[0-9]+`. The workflow fails if the tag ≠ the pom version, or if the version's `CHANGELOG.md` section lacks an `**Index format:**` line.
- Release assets:
  - `pharos-X.Y.Z.jar`;
  - `pharos-X.Y.Z.jar.sha256` (`sha256sum` format: `<hex>  pharos-X.Y.Z.jar`);
  - `pharos`;
  - `setup.sh`;
  - `pharos-skill.tar.gz` (the `.claude/skills/pharos` directory). This one is a plan addition: `setup.sh` installs the skill, and release mode has no checkout to copy it from.
- `setup.sh` verifies with `sha256sum -c` or `shasum -a 256 -c`, replaces installed files with `mv` (new inode), and never overwrites the running script in place.
- Never touch `~/.pharos` in tests: use `@TempDir`. Shell tests use a temp `HOME`.
- `./pharos` stays in sync with new Java commands (CLAUDE.md).
- The plan stops before pushing any tag. Publishing is the maintainer's action.

## Review Focus

1. **A cross-project search where every project is outdated** returns no results with the warnings listing all of them, not an exception or a silent empty list. Test owned by Task 3.
2. **A project re-indexed while the daemon runs** becomes searchable without a daemon restart: the stamp's mtime invalidates the cached check. Test owned by Task 3.
3. **`upgrade-indexes` when a project's root path no longer exists** skips it with the manual command, continues with the others, and exits non-zero. Test owned by Task 4.
4. **`setup.sh --release` with a corrupted download** (checksum mismatch) aborts before touching `~/.pharos/bin`, and the old install keeps working. Test owned by Task 5.
5. **A user downgrading to an older release whose format is lower than their indexes** gets the "newer index" wording, not "run index --full" alone. Test owned by Task 1.

**Interfaces:**
- Produces:

### Task 4: `index-status` and `upgrade-indexes` commands

**Files:**
- Create: `cli/IndexStatusCommand.java`, `cli/UpgradeIndexesCommand.java`
- Modify: `cli/CodeSearchCommand.java` and `Main.java` (`DependencyFactory`) to register both; `pharos` (Python subcommands that spawn the jar, like `cmd_backfill_embedding_cache`)
- Test: `src/test/java/com/pharos/cli/IndexStatusCommandTest.java`, `src/test/java/com/pharos/cli/UpgradeIndexesCommandTest.java`

**Interfaces:**
- Consumes: `IndexFormat` (Task 1); `ProjectIndexManager.index(...)` full runs (Task 2); `ProjectRegistry`, `IndexConfig`.
- Produces:
  - `pharos index-status [--json]`:
    - the JSON is an object with `requiredFormat`, `pharosVersion` and `projects`. Each project entry has `name`, `status`, `format`, `pharosVersion`, `rootPath`, `rootExists`, `indexBytes` (computed by walking the project index dir) and `lastIndexed`.
    - the table output lists the same fields; its layout is the builder's choice.
    - It is strictly read-only: it never starts a daemon or writes files. `setup.sh` (Task 5) parses this exact JSON shape.
  - `pharos upgrade-indexes [--dry-run] [--yes] [--no-embed] [project...]`:
    - **Selection:** outdated or newer projects, optionally filtered to the named ones.
    - **Plan:** prints each project's name, index size, root path and whether embeddings will run (any configured provider and no `--no-embed`).
    - **Confirmation:** `--dry-run` stops after the plan. Without `--yes` it asks `Re-index N projects? [y/N]` on an interactive console (`System.console() != null`). A non-interactive run without `--yes` exits 2 with `use --yes to run non-interactively`.
    - **Execution:** runs `indexManager.index(root, name, false, false, embed, true, listener)` per project in sequence. A project whose root doesn't exist is skipped, printing `re-index manually: pharos index --full <name> <path>`. Other failures are caught, and the run continues.
    - **Summary and exit:** prints a summary (upgraded, skipped, failed) and exits 0 only if nothing was skipped or failed, else 1.

### Task 5: `setup.sh` release mode, upgrade warning and `--upgrade-indexes`

**Files:**
- Modify: `setup.sh`
- Create: `scripts/test-setup.sh`

**Interfaces:**
- Consumes: `index-status --json` (Task 4); `upgrade-indexes --yes` (Task 4); the release asset names (Global Constraints).
- Produces: these `setup.sh` flags.

  | Flag | Behaviour |
  |---|---|
  | `--release latest\|vX.Y.Z` | Download mode (below) |
  | `--yes` | Skip prompts |
  | `--upgrade-indexes` | Run the installed jar's `upgrade-indexes` (`--yes` is passed through), then restart the daemon if it was running |
  | `--skip-build`, `--restart-only` | Unchanged |

  `PHAROS_RELEASE_BASE_URL` (default `https://github.com/nhimanen/pharos/releases/download`; `latest` is resolved via `https://api.github.com/repos/nhimanen/pharos/releases/latest`) lets tests point setup at a local directory over `file://`.

  Download mode:
  1. Download all assets into `mktemp -d`.
  2. Verify the jar checksum. On mismatch, abort with exit 3 before touching `~/.pharos/bin`.
  3. Upgrade warning, which applies in source mode too: before installing the new jar, run `java -jar <new jar> index-status --json`. If any project's status is not `ok`, print the warning block shown in the spec. Without `--yes`, prompt `Continue installing? [y/N]`; when there's no TTY and no `--yes`, abort with exit 2.
  4. Install: `mv` each file into `~/.pharos/bin` (`pharos.jar`, `pharos-cli.py`, `setup.sh`), and unpack the skill into `~/.claude/skills/pharos`.
  5. Restart the daemon as today.
