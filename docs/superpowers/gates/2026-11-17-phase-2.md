## How to run

```bash
mvn clean package -DskipTests
GATE=/home/me/gate2-scratch/run1 GATE_PHASES=cold,cold-models,cold-full,warm,cap \
  systemd-run --user --scope -q -p MemoryMax=9G bash scripts/cluster-gate-phase2.sh
# re-runs against the same published bucket: GATE_REUSE_INDEX=1
```

The script never downloads anything and never writes `~/.pharos` or `~/.djl.ai`. Each JVM gets its own `user.home` and `pharos.home` under `$GATE`. The embedding model is copied into `$GATE/models-home/.djl.ai` (each node home has a symlink to that copy). MinIO runs on 127.0.0.1:9000 and the readers on :7301 and :7302. Readers are started and stopped by PID from `scripts/cluster_gate_phase2.py`, one configuration at a time. Only the warm step runs the lazy and full readers side by side. Phases `cold-models` and `cold-full` are diagnostics and are not gated.

- `--help` prints the usage.
- `--dry-run` prints the plan and starts nothing.
- `python3 -I scripts/cluster_gate_phase2.py --self-test` checks the percentile, ulp, cap and comparison rules against canned inputs.

The bitwise check reopens the full copy with `-Dpharos.lucene.directory=niofs`. That is a diagnostics hook in `LuceneDirectoryFactory.DEFAULT`, added for this gate in commit 70d0e89 with a unit test.

## Cold (20 trials per variant)

Each trial deletes the reader home (block cache, generation dirs, registry) and starts a lazy reader. It waits for "serving 2 shard(s)" and for `/health` ready, then times its own lucene BM25 query (the first 20 distinct lucene queries of `eval/benchmark.py`), then one pharos vector query.

| Variant | lucene first query p50 / p95 / max | vector p50 / p95 | start->serving p50 / p95 | start->ready p50 / p95 |
|---|---|---|---|---|
| `cold`: lazy, as specified (gated) | 4.880 / **5.091** / 5.198 s | 0.170 / 0.184 s | 1.81 / 2.01 s | 1.85 / 2.07 s |
| `cold-models`: lazy, first query after "Search models ready" | 0.703 / **0.764** / 0.785 s | 0.166 / 0.188 s | 1.71 / 1.81 s | 1.76 / 1.86 s |
| `cold-full`: full-mode reader on local files, as specified | 5.198 / **5.246** / 5.320 s | 0.167 / 0.194 s | 1.36 / 1.46 s | 1.41 / 1.50 s |

All 60 trials returned 10 lucene hits and 10 vector hits.

**Dominant cost: the query-model warm-up.**

- `WebCommand` loads the search models (the jina ONNX query embedder) on a background thread at start (`SearchEngine.warmUpInBackground`). Every search first calls `builtPipelines.get()`, which waits for that same one-time load, keyword searches included.
- The warm-up took 4 969–5 110 ms in every trial ("Search models ready (N ms)").
- `/health` turns ready about 1.8 s after start, so the first query blocks on the remaining ~3 s of model load plus its own work.
- The full-mode control, which reads no remote bytes, is just as slow (p95 5.246 s). Once the models are loaded, the lazy reader's cold first query is 0.764 s at p95.

Lazy storage is therefore not what breaks the 3 s bar on this host. As instructed, I recorded the value and stopped for a decision. Possible decisions include:

- make reader readiness wait for the model warm-up;
- define cold time from model-ready;
- move query embedding off the keyword path's critical section.

**What the lazy reader fetched.**

- `/health` `bytesFetched` was 71 656 306 bytes at ready, before any query. The first lucene query added 8 388 608 bytes (one block), and the vector query sometimes added one more block, for a total of 80 044 914 or 88 433 522 bytes.
- Prefetch logged "2 heads and 0 blocks (0 bytes)" for both shards. Both shards are compound files (`.cfs`), so the prefetch extensions (`tip`, `tim`, `vex`, …) never match a file name. The warm open before activation touches nearly every 8 MiB block of the four `.cfs` files, which together hold 88.6 MB.
- Materialisation took 350–555 ms for lucene (6 files downloaded, 2 Lucene files remote; open-before-activate 141–278 ms) and 102–248 ms for pharos.

## Warm

A lazy reader (:7301) and a full-mode reader (:7302, production MMap) ran side by side.

- The queries were the 99 pharos+lucene benchmark queries with `pipeline=keyword`, plus `vector` and `hybrid` on the 45 pharos queries: 189 answers per pass.
- Each side ran one untimed warm-up pass, then 3 timed passes interleaved (lazy/full, full/lazy, lazy/full).

| Pipeline | lazy p50 / p95 / max | full p50 / p95 / max | n per side |
|---|---|---|---|
| keyword (gated) | 24.0 / **36.7** / 58.6 ms | 24.2 / **40.4** / 61.7 ms | 297 |
| vector | 33.3 / 55.5 / 63.7 ms | 37.9 / 67.5 / 73.7 ms | 135 |
| hybrid | 40.7 / 79.6 / 113.5 ms | 41.6 / 76.0 / 99.5 ms | 135 |

- **Ratio:** keyword p95 ratio 0.908, against a limit of 1.10. **PASS**
- **Startup:** serving/ready at 2.17 / 2.22 s for lazy and 2.22 / 2.26 s for full. The NIOFS reopen took 2.56 / 2.87 s.
- **Lazy cache after the run:** 88 433 522 bytes on disk out of 8 GiB; 2 228 514 hits, 14 misses (hit rate 99.9994%); 0 evictions.

**Top-10 checks.** Each check compares every field of every result: id, order, float32 score bits, label, signature, javadoc, file path, lines, snippet, and so on.

- **Lazy vs MMap full copy:** 189 / 189 bitwise identical, including all 90 vector and hybrid answers. **PASS**
- **Lazy vs the same full copy reopened with NIOFS:** 188 / 189. The one mismatch is `vector|pharos|BordaMerger`, rank 3 `PipelineFactory#resolveMerger(String)`: lazy and MMap score it 0.6311579, NIOFS scores it 0.63115793. That is 1 ulp, with the same id and order. The cap run's lazy reader reproduced it exactly on both passes.
- All 189 answers were non-empty.

**Cause of the NIOFS mismatch (the ruling's premise does not hold here).**

- The Task 3 ruling assumed lazy reads score like NIOFS, with MMap off by about 1 ulp.
- On this index, the lazy reader matches MMap bit for bit on every answer, and NIOFS is the odd one out.
- One process, one full copy, 300 query vectors, k=30 (`KnnFloatVectorQuery` on `vec.jina-code-v2`): MMap and NIOFS scores differed in 2 407 of 9 000 (max 2 ulp), with 0 order differences.
- Only one of the 90 vector/hybrid top-10s shows this, because the API rescores top results with the chunk vectors (`LateInteractionRescorer`). Only first-pass fallback scores depend on the directory.
- This is not query-embedding noise: the other 9 scores of that answer are bitwise equal, and three separate reader processes produced the same values.

The strict criterion as written ("bitwise vs NIOFS") fails. Read as intended ("lazy returns exactly what a full copy returns"), it passes against the production MMap copy, which is stronger than the 4 ulp tolerance. The decision is held: restate the strict check as bitwise against MMap, or keep NIOFS and accept 1-ulp first-pass diffs.

## Cap

- **Configuration:** `cacheMaxBytes` = 50% of the lucene shard's Lucene bytes (53 142 359), rounded down to a block multiple. With the default 8 MiB block that would be 24 MiB, only 3 blocks, which is below the config minimum of 4 x block. So the block size was halved to 4 MiB: **cacheMaxBytes 25 165 824 (24 MiB), blockSizeBytes 4 194 304, maxConcurrentFetches 16**, bound 92 274 688.
- **Cache shared by both shards:** the cache also holds pharos (35.5 MB of `.cfs`), so the working set (88.6 MB) is 3.5 x the cap.
- **Run:** all 189 queries, twice, with `/health` sampled every second (64 samples).

Results:

- **Max `bytesOnDisk`: 25 165 824**, exactly the cap, never above. **PASS.** The final sample was 22 710 189.
- **Top-10:** 189 / 189 bitwise identical to MMap on pass 2 (**PASS**). Against NIOFS, 188 / 189 on both passes, the same 1-ulp vector answer as in the warm step.
- **Hit rate:** 99.73% of block lookups (1 111 526 hits, 2 956 misses), 3 010 evictions, **11 432 766 600 bytes fetched**: about 129 x the working set in two passes, so the cache thrashed heavily. The hit rate counts lookups, and many reads land in each block lease. Its high value hides the thrash. Bytes fetched is the operator-relevant figure.
- **Reader start:** serving/ready at 1.61 / 1.77 s.

## Findings

1. **Vector search returns nothing on indexes built with the legacy top-level `embeddingModelUrl` config (pre-existing, also on `main` 6400137).** Indexing goes through the multi-model path. `DocumentMapper.attachVectorFields` writes `vectorFieldName("legacy")` = `vec.legacy`, but search reads `vectorFieldFor("legacy")` = `vectorEmbedding` (`VectorSearchStrategy`, `UnifiedRetrievalStage`). The first pharos publish (gen 1; 4 734 docs) has a 768-dim field `vec.legacy` and no `vectorEmbedding` field, and every vector query on the writer and on the readers answered 0 hits with no warning. The user's own `~/.pharos/config.json` uses this legacy shape. The gate works around it with an explicit `modelId` and records the bug here. It is not fixed on this branch.
2. **Prefetch extensions never match compound-file segments.** Both published shards are two `.cfs` segments each, so prefetch fetches 0 blocks. With 8 MiB blocks, the warm open before activation downloads about 81% of all `.cfs` bytes anyway (71.7 of 88.6 MB). With smaller blocks, cold behaviour would depend on prefetching the sub-file ranges inside `.cfs`, which is a code change.
3. **The cold first query waits for the model warm-up** (about 5 s with jina on this host), whatever the storage mode. See Cold.
4. **Thrash at a 50% cap** is safe (the cap held exactly, and results were identical) but costly: 11.4 GB fetched. The eviction WARN fired twice, 60 s apart. The first, at 14:17:31.639 during the warm open, reported hit rate 74.1% (20 hits, 7 misses, 1 eviction). The second, at 14:18:31.648, reported 99.7% (1 044 536 hits, 2 794 misses, 2 848 evictions). Its hit rate looks healthy while the cache thrashes, so bytes fetched (or misses per minute) would be a better signal than the hit rate.
