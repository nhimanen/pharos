### Backlog latency: why it fails

22 of the 47 changes were first seen in the backlog (or already published) more than one poll (10 s) after the push. I classified each by what the shard's lease holder was doing between the push and the sighting:

| Class | Changes | Latency |
|---|---|---|
| holder idle (no other run) | 12 | 10.1–13.3 s |
| holder running this shard's own run when the push landed | 2 (lucene #7, #11) | 140.0 s, 19.2 s |
| holder running another shard's run | 8 | 11.1–170.2 s (beta #6 170.2 s and #10 49.4 s, alpha #36 36.9 s, each behind a lucene run on w4) |

There are three causes, all in `WorkLoop.tick`:
1. **The poll is a fixed delay after the tick.** `scheduleWithFixedDelay(tick, pollSeconds)` runs the next poll `pollSeconds` after the previous tick *ends*, and the pending flag reaches the bucket with the next heartbeat. So even an idle writer sees a change up to `pollSeconds` + tick time + `heartbeatSeconds` after the push (measured: up to 13.3 s against 10 s).
2. **A writer polls its shards only between runs.** `tick()` polls every held shard, then runs the pending ones one at a time. While one run is going (a lucene FULL here takes about 4 min after a takeover), changes to the writer's other shards are neither detected nor reported.
3. **A change pushed during a shard's own run** is seen only after that run publishes.

This is not a small, clearly in-scope fix: reporting pending changes during a run needs polling on its own thread (or polling between parse chunks), with care for the shard state the loop thread owns. I did not change it. Options for the decision:
- (a) poll held shards on a separate thread and beat right after each poll, so the backlog is current during runs (runs still serialise per writer);
- (b) restate the bar as "within one poll interval plus one heartbeat after the writer's next poll", and accept that a writer's shards wait behind its running run (then the idle measurements pass: 13.3 s ≤ 15 s, and only the 8 "behind a run" cases and the 2 "own run" ones remain).

## Fix found by the gate (committed: 25e0024)

**A shard indexed `--no-embed` was embedded by work-queue writers.** `ClusterRuntime.beginWriting` builds the work loop with `embed = true`, and nothing per shard said otherwise. So the first work-queue owner of lucene (recorded by `pharos index --no-embed --source-git …`) would have embedded all 56 k methods: hours with jina on this host, which contradicts the plan's "lucene (`--no-embed`)" setup.
- The fix: the catalog source carries `"embed": false` (absent means true, so older catalogs read the same). `pharos index --no-embed --source-*` records it, and the work loop's runs and the disk-guard estimate for that shard skip embeddings.
- Tests: `WorkLoopTest.shardRecordedWithoutEmbeddingsIsIndexedWithoutThem` (mutation-checked: fails with the old `settings.embed()`), `ObjectStoreCatalogTest.noEmbedSourceIsRecordedAndReadBack`, and `SourceOptionsTest` now expects the flag.
- `pharos publish --source-*` still records `embed: true` (it has no `--no-embed` flag).

## Other findings

1. **Every writer loads the search model at `pharos web` start.** `WebCommand` warms the search models on every role, so a writer loads jina (about 1.1 GB) although it serves no search. The gate set `searchEmbeddingModel` to a name no provider has, so writers resolve to no search model and load jina only when they embed. Backlog: skip the search-model warm-up on `role: writer`.
2. **Takeovers on one host are always FULL.** Each writer's `workDir` path differs, so the restored index is rebuilt by a full parse (lucene: about 4 min including restore with a 2g heap). Embeddings come from the restored cache, so this costs parse time, not provider calls. With one shared `workDir` path (containers) the takeover would be incremental. Not exercised here.
3. **The default `minFreePercent` of 10 %** makes a writer low on any large, mostly full disk (here 10 % of 233 GB is 23.3 GB, against 27 GB free). Operators of shared disks will need `minFreePercent: 0` and an absolute `minFreeBytes`; worth a README note.
4. **The heartbeat's `indexing.progress` stays at 1.0 into the commit phase** (K1 was killed at "commit, progress 1.0"): `Mining synonyms` reports no progress, so the bar keeps the `Indexing` value.
5. **w5 got no shard at three writers**: ceil(4/3) = 2 and both holders had exactly 2. This is the fair-share rule working as designed, but a new writer can sit idle until the writer count divides the shards differently.

**The stop:**
- At 21:12:06 the kernel's memcg OOM killer killed a gate java with 2.5 GB anon RSS, inside the scope `run-p276126-i276643`. That was most likely w2: the last memory sample had w2 at 2 493 MiB and w4 at 2 220 MiB.
- systemd then failed the scope (`oom-kill`), and its SIGTERM ended the driver. The launcher exited 143.
- The watchdog then stopped the recorded leftovers. Its MemAvailable floor never triggered; host MemAvailable stayed at 4.1 GiB or above.
- The OOM stayed inside the gate's scope; no process outside it was touched.

The gate's own memory:
- The scope's peak was 6 G.
- Two writers each ran a FULL lucene index after a takeover (2.2–2.5 GB each with a 2g heap; each takeover is a full run because every writer has its own `workDir`).
- The readers took 0.4–0.48 GB each, the router 0.24 GB, plus MinIO and the driver.
- The 6G estimate did not allow for two concurrent lucene full runs. A cap of about 7.5G, or `GATE_WRITER_HEAP=1536m`, would.

**Host load during the run** was 54–87 (load average, 16 cores), from the user's benchmark and match simulations.
- MinIO calls timed out. At 20:59:32–33, w5 and w6 lost their leases (`putIfMatch … timed out after PT5S`), and heartbeats and source polls failed (`S3 put/get failed`).
- The timing criteria of this run (writer count within one heartbeat, backlog within one poll) are therefore not meaningful, and were not computed.

**Finding, not judged, needs a look:** w6 lost its lucene lease 55 s into a FULL lucene run and logged nothing after it, not even on SIGTERM. w5 had nothing running and still did not exit within 120 s. Possible causes:
- On a saturated host, the drain (`cluster.drainSeconds` 20) plus the lease release and heartbeat delete (S3 calls with 5 s timeouts, retried) may take longer than 120 s.
- Or a run that lost its lease is not aborted, so the shutdown waits for a safe point that a parse phase does not reach.
