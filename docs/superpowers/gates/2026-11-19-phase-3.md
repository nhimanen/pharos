## Ranking

The queries are the 99 pharos+lucene queries from `eval/benchmark.py` (99 distinct texts; 45 pharos, 54 lucene), with limit 10. Every pipeline ran once to warm up and then once measured.

### Scope deviation, recorded

The brief asks for every pipeline with no project filter. That cannot be compared fairly for the vector-bearing pipelines.

The single-node reference refuses an unscoped hybrid, hybrid-reranked or vector query when one project has no vectors of the search model. It answers HTTP 500 `VectorModelUnavailableException: Project 'lucene' has no vectors for search embedding model 'jina-code-v2'` (297 of 297 such answers in run 1, which used the brief's spec). The cluster instead answers 200 with the warning `shard lucene has no vectors for model jina-code-v2`.

Embedding lucene (56k methods) was not feasible on this host. So the comparison uses two scopes:

- **keyword:** all 99 queries, unscoped, coordinated on R1 {pharos}, so lucene goes to R2 or R3. This is as briefed.
- **hybrid, hybrid-reranked, vector:** all 99 texts scoped to `project=pharos`, coordinated on **R2 {lucene}**, so the pharos shard is remote. The gate is on the 45 pharos-origin queries, as the task notes say ("use the pharos queries where vectors exist"); all 99 texts are reported too.
  - This exercises the coordinator, embedding the query once, and the remote shard calls.
  - It does **not** exercise the multi-shard two-round vector or unified merge against a reference, because no single-node answer exists for it.
  - Unscoped hybrid and vector on R1 answered 99/99 with HTTP 200, all non-empty, each carrying the "no vectors" warning.

## Keyword failure: causes (found, not tuned)

Twelve of the 99 queries differ in some score: 4 in their ids, and 8 more in scores only. There are two independent causes.

### A. Implicit project-name boost uses only the coordinator's local projects (product bug)

This causes 2 of the 4 id failures.

`SearchEngine.searchWithTrace` builds `knownProjects` from `registry.listAll()`, which lists only the shards the node holds. When a query mentions a project name (here "Lucene"), the single node multiplies that project's results by `IMPLICIT_HINT_BOOST` = 1.3. R1, which holds only pharos, does not know `lucene`, so it never applies the boost.

Evidence:
- In "close Lucene index reader after search", every lucene result scores exactly 0.76923 = 1/1.3 of the reference's: IndexReader, TaxonomyReader, IndexSearcher, DirectoryReader, CloseReaderTask and TestIndexReaderClose. The pharos results are unchanged.
- "find code that maps a parsed method to a Lucene document" shows the same pattern (MoreLikeThis × 0.76923).

The same gap affects an explicit `lucene:query` prefix on a coordinator that does not hold lucene. That prefix would be neither stripped nor boosted; this was not measured.

Fix direction: build `knownProjects` from the routing catalog's shards on a coordinator.

### B. Synonym statistics across shards (documented approximation)

This causes the other 2 id failures and most of the score-only differences.

The README already lists the approximation: "a synonym present only on another shard is left out of a shard's synonym statistics". Indexing auto-mined class-name synonyms from each project, so a query term expands to a term that exists in only one shard. Examples from `synonyms.txt`:

| Query term | Expands to (mined from) |
|---|---|
| `indexwriter` | `indexwriterparsetest` (pharos) |
| `synonymprovider` | `word2vecsynonymprovider` (lucene) |
| `atmost`, `atmostn` | `atmostnvalueshighlighter` (lucene) |
| `anunsupported` | `manifestvalidation` (pharos) |

In every affected case, the docs whose scores differ are those expansion targets:

| Query | Doc | Fan-out / reference |
|---|---|---|
| "IndexWriter" | IndexWriterParseTest | 1.0345 |
| "SynonymProvider" | Word2VecSynonymProvider and its methods | 1.007–1.036 |
| "…most relevant passages for highlighting" | AtMostNValuesHighlighter | 1.0597 (id swap at ranks 7–8) |
| "daemon startup health check" | ManifestValidation#check | 1.0519 (id swap at ranks 7–8) |
| (other queries) | CandidateShaper, FindMethodsByPartialFqnTest, QueryNodeProcessorPipeline | 1.015–1.079 |

Fan-out scores are always slightly higher. Two score-only cases (`IndexConfig#resolvedParseThreads`, `ConceptMiner#uniqueTerms`) are not synonym targets themselves. They are consistent with the graph-boost normalisation (max in-degree over the merged top 10) shifting when another candidate's raw score moves.

With A fixed, the keyword result would be at most 97/99 = 97.98%, still below 98%. B alone keeps the criterion from passing on this corpus, with its auto-mined synonyms. Synonyms were not disabled to re-measure; doing so would change the setup.

### Decision needed

- (a) Fix A (catalog-wide `knownProjects`), and either
  - (b1) make synonym statistics global (for example, ship the expanded terms' statistics in the term-statistics round),
  - or (b2) accept B as the documented approximation and restate the keyword bar for corpora with cross-shard synonyms.
- Separately, decide whether the vector-family scope deviation above is acceptable, or whether the multi-shard vector merge needs a reference, which would mean an embedded lucene or a second embedded project.

## Other findings

1. **The catalog-age warning appears after idle periods.** Two warnings:
   - `routing with a catalog 165 s old` on the first unscoped hybrid on R1, after the ranking runs;
   - `routing with a catalog 112 s old` on the first elasticity request.

   The README says the catalog is re-read in the background every 5 s, but here it had aged past the 60 s warning threshold while the readers were busy answering scoped queries, or idle. Possible causes: the refresh only runs when unscoped routing asks for it, or the age is not reset when the catalog is unchanged. Not investigated further.
2. **Single-node refusal versus cluster warning.**
   - A single node answers 500 for an unscoped vector query when any project lacks the model's vectors.
   - A coordinator holding both shards takes the local path and does the same.
   - A coordinator missing one of them answers 200 with a warning.

   So the same query succeeds or fails depending on which reader the router picks. This is pre-existing single-node behaviour, but behind a router it is inconsistent. The elasticity mix avoids it on purpose.
3. **Seeding the embed cache saved little:** 26 min of embedding remained, against Phase 2's 35 min.

## Carried minors (commit 44881ed)

- **Router.**
  - The forwarded exchange now has one total deadline: response headers and the capped body read together, bounded by the 120 s request timeout. On a timeout the router answers 504 and does not resend. A header timeout also maps to 504.
  - The capped body subscriber is shared with `ShardClient` (`com.pharos.cluster.internal.CappedBody`); a declared length over the cap is not read at all.
  - Test: `routerBoundsTheWholeExchangeIncludingABodyThatStalls` checks that a reader sending its headers and then stalling the body for 5 s gets a 504 within 3 s (deadline 0.8 s) and is not resent. It was **red before the change**: it got 200 after 5.0 s.
  - RouterCommandTest 6/6; DistributedSearchTest and the shard and internal tests are green.
- **README and CHANGELOG.** The stop timeout must be above `drainSeconds` + 15 s (`NativeInferenceGuard.DRAIN_TIMEOUT_MS`, the wait for running model calls) plus a margin: Kubernetes `terminationGracePeriodSeconds` above 35 with the defaults, e.g. 45. The router's 504 is documented.
